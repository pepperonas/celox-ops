# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

celox ops is a full-stack business management webapp for freelancers/IT consultants. German-language UI. **Multi-user with isolated workspaces** (per-user `owner_id` data isolation; admin-managed accounts, no public registration; JWT auth). Manages customers, orders, contracts, invoices (with PDF generation), leads, time tracking, expenses, the **Rainmaker** acquisition-activation module, and integrates with the Claude Token Tracker for AI usage transparency. The frontend uses a **Material Design 3 Expressive** dark theme.

## Commands

### Production
```bash
docker compose up -d --build          # Build and start all services
docker compose up -d --build backend   # Rebuild backend only
docker compose up -d --build frontend  # Rebuild frontend only
docker compose up -d backend           # Recreate ohne Rebuild — nötig für .env-Änderungen! (restart übernimmt sie NICHT: Container behält seine Start-Umgebung)
docker compose down                    # Stop all
```

## Architecture

### Backend (Python 3.12, FastAPI)
- **Entry point**: `backend/app/main.py` — FastAPI app with lifespan (creates tables + starts hourly cron)
- **Config**: `backend/app/config.py` — Pydantic Settings, all from `.env`
- **Database**: `backend/app/database.py` — async SQLAlchemy 2.0 with asyncpg, connection pooling
- **Auth**: `backend/app/auth.py` — JWT (python-jose), DB-backed `users` table, OAuth2PasswordBearer. `get_current_user` returns the `User` and sets the `current_owner_id` ContextVar (see Multi-tenancy). `require_admin` gates admin endpoints. `.env` admin is bootstrapped into a real DB user on first start. **Google-Login ("Sign in with Google")**: `POST /api/auth/google` verifiziert das GIS-ID-Token (google-auth: Signatur/exp/aud gegen `GOOGLE_CLIENT_ID` aus .env; `validate_google_claims` prüft zusätzlich iss/email_verified — DB-frei getestet) und meldet den Benutzer an, dessen `users.google_email` (unique, case-insensitiv verglichen, via manuellem `ALTER` migriert) zur E-Mail passt. Kein Auto-Signup (403 für unverknüpfte Konten); TOTP wird bei Google-Login bewusst nicht zusätzlich verlangt. Leere `GOOGLE_CLIENT_ID` ⇒ 503 + Button ausgeblendet (Login.tsx lädt das GIS-Script nur, wenn `GET /api/auth/info` eine `google_client_id` liefert — Laufzeit-Konfig, kein Frontend-Rebuild bei Änderung). JWKS-Fetch läuft via `asyncio.to_thread`; Rate-Limit 10/min/IP. Deps: `google-auth` + `requests`. Verknüpfung pflegt der Admin über `PATCH /api/users/{id}` (`google_email`; "" entfernt sie).
- **Multi-tenancy invariants (important)**: (1) **Public endpoints and background jobs** run with the ContextVar UNSET → queries are UNSCOPED (global). Any public route that returns owned data MUST resolve the user and `current_owner_id.set(user.id)` itself (see `routers/ical.py`, which authenticates via per-user `users.ical_token`). The cron (`run_cron`) sets the ContextVar per active user for the Rainmaker reminder; `check_overdue_invoices` is intentionally global. `backup.py` export sets it to `None` for a true full dump. (2) **Invoice numbers are unique PER OWNER** (`uq_invoice_owner_number`), not globally — `generate_invoice_number` is owner-scoped so each user has their own sequence. It takes a per-owner `pg_advisory_xact_lock` (held to commit) so concurrent creates (double-submit, or cron vs. the manual generate endpoint) serialize instead of colliding on the unique constraint; `flush_new_invoice` is a SAVEPOINT-based retry safety net. (3) When accepting an FK id (customer/order/contract/…) in a request body, validate it with a scoped `select` (returns None if it belongs to another tenant) before assigning — `with_loader_criteria` only hides rows on SELECT, it does not validate inserts.
- **Multi-tenancy / data isolation**: `backend/app/tenancy.py` — every owned model uses `OwnedMixin` (`owner_id` FK→users). A request-scoped `current_owner_id` ContextVar (set in `get_current_user`) drives two SQLAlchemy session events: `do_orm_execute` auto-filters every ORM SELECT (incl. column aggregates) to the owner via `with_loader_criteria`, and `before_flush` auto-stamps `owner_id` on new owned objects. Unset ContextVar (login, lifespan bootstrap, cron) ⇒ unscoped/global. **So routers generally need NO manual owner filtering** — but caches must be per-owner (e.g. dashboard `_stats_cache` is keyed by `owner_id`). `users`/`audit_log`/`document_templates` are global (not owned). Owned-model list is registered in `main.py` (`set_owned_models([...])` + `install_tenancy_events()`).
- **Pattern**: Each module has model → schema → router. All routers registered in main.py after app creation (to avoid circular imports).
- **Models inherit from `Base`** defined in `models/customer.py`. New models MUST import Base from there.
- **All list endpoints return paginated**: `{items: [], total, page, page_size, pages}` — NOT plain arrays. Exception: `GET /api/attachments` returns a plain list.
- **UUIDs**: All primary keys are UUID (asyncpg uses its own UUID type — serialize with `str()` for JSON).
- **Enum values**: Stay ASCII in code (`ueberfaellig`, `gekuendigt`, `halbjaehrlich`). German umlauts only in user-facing text/labels.
- **PDF generation**: WeasyPrint + Jinja2 templates in `backend/app/templates/`. Signature loaded as base64. Footer uses `@page @bottom-center` (not position:fixed).
- **Cron**: Background asyncio task in lifespan, hourly. Globally: marks overdue invoices (`check_overdue_invoices`). Then **per active user** (ContextVar scoped): Rainmaker daily reminder + **auto-recurring invoices** (`services/invoice_service.generate_due_recurring` — creates draft invoices for due contract billings; idempotent via `last_invoiced_date`, same logic as `POST /api/invoices/generate-recurring`).
- **Backup export** (`routers/backup.py`): Auto-discovers all tables via `Base.registry.mappers` — no manual list needed for new tables.

### Zahlungsabgleich per Kontoauszug (2026-07)

Zahlungen wurden von Hand gebucht. Jetzt: Auszug einlesen → Zuordnung → **Bestätigen**. `services/bank_import.py` ist rein (kein Netz, keine DB) und damit vollständig testbar.
- **Formate:** **camt.052/053/054** (ISO 20022; namensraum-unabhängig gelesen, mehrzeilige `Ustrd`-Verwendungszwecke werden zusammengefügt, Gegenpartei = `Dbtr` bei Gutschrift) und **CSV** über **Spalten-Aliase** (`_COL_DATE/_COL_AMOUNT/_COL_PURPOSE/_COL_PARTY/_COL_TYPE`) statt Sonderfällen pro Bank — deckt Sparkasse/DKB/Volksbank/Commerzbank/N26 ab, überspringt Vorspann-Zeilen und erkennt das Trennzeichen selbst. `parse_amount` unterscheidet deutsche und englische Schreibweise am **letzten** Trennzeichen. Ein ausdrückliches **Soll/Haben-Kennzeichen** (`is_credit_marker`, DATEV-Stil mit vorzeichenlosen Beträgen) schlägt das Vorzeichen — ohne das galt jede Zeile als Gutschrift, und eine Ausgangszahlung mit Rechnungsnummer im Zweck wäre als Zahlungseingang vorgeschlagen worden. **Das Format wird am Inhalt erkannt, nicht an der Endung** (umbenannte Exporte sind häufig).
- **Zuordnung dreistufig** (`match_transactions`): `exact` = Rechnungsnummer im Verwendungszweck/Referenz **und** Betrag = offener Rest · `number` = Nummer erkannt, Betrag weicht ab (Teil-/Überzahlung, offener Rest wird genannt) · `amount` = keine Nummer, aber **genau eine** offene Rechnung mit exakt dem Betrag. **Mehrdeutiges wird nicht geraten**, sondern mit Begründung als offen ausgewiesen; **jede Rechnung erscheint höchstens einmal** (bester Treffer gewinnt) → „alle bestätigen" kann nie doppelt buchen. Belastungen werden gezählt, aber nie zugeordnet. Nummern-Erkennung ist tolerant gegenüber Trennzeichen (`CO-2026-0007`, `co 2026 7`, `CO/2026/0007`) und nutzt das Präfix aus `app_settings.invoice_prefix` plus die Präfixe der offenen Rechnungen.
- **Endpoints:** `POST /api/invoices/bank-import/preview` (multipart) → Vorschläge + nicht zugeordnete Buchungen; `POST /api/invoices/bank-import/apply` bucht die **bestätigten** Zeilen wie die manuelle Zahlungserfassung (`amount_paid`, Status → bezahlt bei Vollzahlung, Aktivität mit Bankreferenz) und liefert den Zahlungsstand **vor** der Buchung zurück → das bestehende `PUT /invoices/{id}/payment-state` ist das Undo. Owner-scoped Selects; Gutschriften nehmen keine Zahlungen auf.
- **Sicherheit:** Uploads sind nicht vertrauenswürdig. Der stdlib-XML-Parser löst keine *externen* Entities auf, ist aber für **Entity-Expansion** anfällig — deshalb werden `DOCTYPE`/`ENTITY` **vor** dem Parsen abgewiesen (schließt das ohne zusätzliche Abhängigkeit; `defusedxml` wäre die Alternative) plus 10-MB-Deckel. Bewusst **kein FinTS/Bank-API**: kein Zugangsdaten-Risiko, ein Bruchteil des Aufwands.
- **UI:** `pages/invoices/BankImportModal.tsx` (Dropzone am ganzen Dialog, Vorschlagsliste mit Sicherheitsstufe + Tooltip-Begründung, **nur `exact` ist vorgewählt**, nicht zugeordnete Buchungen aufklappbar), Knopf „Kontoauszug einlesen" im Rechnungs-Header, Undo-Toast nach dem Buchen. Tests: `test_bank_import.py` (26).

Kategorie via `category_for` (domain/hosting/sonstige).
  - **Nachträglich umbenennen:** `POST /expenses/hostinger/relabel` setzt bei **bereits importierten** Buchungen nur **Beschreibung + Notiz** neu (Betrag/Datum/Kategorie bleiben). Nötig, weil der Import über `external_ref` idempotent ist — Zeilen, die noch „Domain .de" heißen, würden sonst für immer übersprungen. Die Vorschau zeigt je Zeile „gebucht als X → wird Y" (`_mark_duplicates` trägt die gespeicherte Beschreibung mit), der Dialog hat dafür einen eigenen Knopf. **Kein separates Undo:** der Rückweg ist ein erneuter Lauf mit korrigierter Zuordnung. - **Idempotenz — drei Ebenen, alle in Prod gemessen:** (1) die **Vorschau** markiert bereits importierte Zeiträume, wählt sie nicht vor und sperrt die Auswahlbox; (2) der **Import** prüft serverseitig erneut (`skipped_duplicates`); (3) der **partielle Unique-Index** `(owner_id, external_ref) WHERE external_ref IS NOT NULL` (Migration `scripts/add_expense_external_ref.sql`) ist die letzte Instanz — fünf *gleichzeitige* Anlagen mit demselben Schlüssel ergaben 1×201 + 4×409 und genau eine Zeile. Ein zweiter Importlauf über **alle** Positionen: `created 0, skipped 27`, Bestand und Summe unverändert.
  - **Der Schlüssel hängt an der PERIODE, nicht am Tag** (`period_bucket`): Jahresabo → `hostinger:<abo>:2026`, Monatsabo → `…:2026-07`, kürzere Perioden behalten den Tag (dort *ist* er die Periode). **Warum:** der erste Entwurf war tagesgenau, und Hostinger richtet Verlängerungstermine nachträglich aus (derselbe Effekt, der `last_billed_on` beschäftigt) — eine Verschiebung von `next_billing_at` um 1–10 Tage ergab **11 verschiedene Schlüssel für eine einzige Abrechnung**, der nächste Import hätte sie erneut gebucht. Deshalb gibt „Rückgängig" die Herkunft mit zurück (s. Gotcha zum Löschen). Dadurch löst nginx die Upstream-Container **pro Request** neu auf, statt die IP beim Start zu cachen — ein neu gebauter Container (neue IP) wird sofort gefunden, **ohne nginx-Restart**. Früher zeigte nginx nach jedem Rebuild auf die tote alte IP → 502-Fenster (fehlgeschlagene Lazy-Chunk-Imports im offenen Tab). **Wichtig:** variable `proxy_pass` OHNE URI-Teil leitet die Original-URI unverändert weiter (Location-Präfix == Upstream-Präfix, daher kein Rewrite nötig). **Bind-Mount-Inode-Bug:** `nginx/default.conf` ist als einzelne Datei gemountet → `git pull` ersetzt den Inode, `docker compose restart nginx` übernimmt die neue Config NICHT (alter Inode bleibt gemountet); nur `docker compose up -d --force-recreate nginx` bindet die neue Datei ein. `scripts/auto-deploy.sh` macht das jetzt automatisch bei `nginx/`-Änderungen.
- **ZWEI nginx-Ebenen (wichtig für Timeouts):** (1) der **öffentliche System-nginx** des VPS (`/etc/nginx/sites-available/ops.celox.io`, NICHT im Repo, Certbot-TLS) proxyt `ops.celox.io` → `127.0.0.1:8090`; (2) der **Docker-nginx** (`nginx/default.conf`, im Repo) → `backend:8000`. Ein langes Request (KI-Web-Suche) muss auf **beiden** Ebenen ein hohes `proxy_read_timeout` haben, sonst 504 obwohl das Backend fertig wird. Beide haben seit 2026-07-28 eine Location **`/api/rainmaker/`** mit **300s** (Default sonst 60s außen / 180s innen). Vorher galt das nur für `discover/ai/` — die Vision-Läufe (Chat-Import, Lead-Erfassung aus Screenshots) wären mit sechs Bildern nach 60 s als 504 abgebrochen, obwohl das Backend fertig wird. Ein hohes Read-Timeout ist nur eine Obergrenze und bremst schnelle Routen nicht. Ändert sich das äußere vhost, per SSH editieren + `nginx -t && systemctl reload nginx` (Backup anlegen). - **Gestellte Rechnungen sind inhaltlich unveränderlich (GoBD, 2026-07)**: `DELETE` war schon auf Entwürfe beschränkt, **`PUT /invoices/{id}` prüfte den Status nicht** — eine gestellte/bezahlte Rechnung ließ sich in Positionen, Rabatt, USt, Datum und Kunde ändern, das PDF wurde neu erzeugt, die Nummer blieb gleich (das beim Kunden liegende Dokument wich damit still von der gespeicherten Fassung ab). `services/invoice_lock.py` (rein, testbar) sperrt ab `status != entwurf` **jedes** Feld aus `InvoiceUpdate` — alle erscheinen im PDF, auch `notes` (→ „Hinweis:"). Unberührt bleiben Statuswechsel, Zahlungseingang und Mahnstufe — eigene Endpunkte, die den *Vorgang* dokumentieren, nicht den *Inhalt*. Korrekturweg = **Stornieren (Gutschrift) + Duplizieren**. - **Storno = Gutschrift (`POST /invoices/{id}/credit-note`, überarbeitet 2026-07)**: Eine gestellte Rechnung wird nie inhaltlich „zurückgesetzt" — sie wird durch eine **Gutschrift** storniert. Die erzeugt einen Datensatz mit **eigenem Nummernkreis `GS-YYYY-NNNN`** (`generate_credit_note_number`, per Advisory Lock serialisiert wie die Rechnungsnummer), gespiegelten Beträgen (`build_credit_note_positions`: `-abs` über Decimal, `menge`/Text bleiben), `is_credit_note=True`, `credit_note_for` (FK) **+ `credit_note_for_number`** (denormalisiert für PDF/Anzeige, Migration `scripts/add_credit_note_number.sql`). **Die Rechnungsnummer des Originals bleibt immer bestehen** und wird nie neu vergeben. **Status-Logik (`credit_note_statuses`, entscheidend für korrekte Zahlen):** Original `bezahlt` → beide bleiben `bezahlt` (Netting: +X/−X, Rückfluss im Monat der Gutschrift); Original `gestellt`/`ueberfaellig` → **beide `storniert`** (Neutralisierung — `storniert` zählt weder in der EÜR (nur `bezahlt`) noch in offenen Forderungen). **Frühere Bugs (gefixt):** GS bekam hart `bezahlt` → negativer Phantom-Umsatz in der EÜR bei nie bezahlten Rechnungen, Original blieb offene Forderung; `tax_exempt` wurde nicht kopiert → Kleinunternehmer-Gutschrift wies 19 % USt aus; kein PDF; keine Nummern-Serialisierung. Löschen), **`mitarbeiter`** (arbeitet IM Bereich eines anderen, **ohne destruktive Rechte**). Kern ist `users.works_for_id` (FK→users, `SET NULL`, Migration `scripts/add_user_workspace.sql`, **vor Deploy** — sonst bricht der Login): `models/user.py::workspace_owner_id(user)` = `works_for_id or id` ist die **einzige** Stelle, die den Mandanten auflöst, benutzt von `get_current_user` und dem iCal-Feed. **Der Cron läuft nur für Bereichs-Inhaber** (`works_for_id IS NULL`) — sonst würden Reminder und Vertragsrechnungen pro Bereich doppelt ausgelöst. **Löschsperre serverseitig in `middleware/permissions.py`** (nicht pro Route, damit keine vergessen wird): jedes `DELETE /api/*` + Denylist destruktiver POSTs (`duplicates/merge`, `merge-batch`) → 403. Die Rolle wird **gegen die DB** geprüft, nicht gegen einen JWT-Claim (sonst würde eine Herabstufung erst nach Token-Ablauf greifen). Frontend blendet **alle** Lösch-Aktionen über `utils/permissions.ts::canDelete` aus (Lead, To-do, Kunde, Aktivität, Auftrag, Rechnung, Vertrag, Ausgabe, Anhang, Zeiteintrag, E-Mail-/Rainmaker-Vorlage, Ziel, Duplikate-Merge). Zusätzlich zeigt ein **globaler 403-Interceptor** in `api/client.ts` die Klartext-Begründung des Servers als Toast (feste id `forbidden`) — so läuft auch ein handgebauter Request nicht in eine generische Fehlermeldung. Tests: `test_permissions.py` + `permissions.test.ts`.

**Rolle „Verkäufer" (`verkaeufer`, 2026-07-29):** arbeitet IM Bereich eines anderen (`works_for_id` Pflicht, wie `mitarbeiter`) und sieht dort **nur** die Pipeline plus die Akquise-Vorlagen lesend. Darf Leads anlegen, ändern **und löschen** — das Löschen ist bewusst erlaubt (Aussortieren ist Kernarbeit im Vertrieb), aber umkehrbar und gedeckelt. Kein E-Mail-Versand, keine kostenpflichtigen KI-Funktionen, keine Massen-Importe, kein Merge.
- **Erlaubnisliste statt Verbotsliste (`middleware/role_scope.py`, deny-by-default):** Das übrige Rechtemodell arbeitet mit Verboten (`require_admin` pro Router, Löschsperre). Für eine Rolle, die nur einen Ausschnitt sehen darf, ist das die falsche Richtung — sie wäre standardmäßig überall drin, und **jede künftig hinzugefügte Route wäre ein neues Leck**. `allowed_for_role(role, method, path)` ist rein/testbar; Muster matchen den **ganzen** Pfad (`fullmatch`), damit `/leads` nicht `/leads/trash` mitfreigibt (als Test festgenagelt). Nicht zugeschnittene Rollen bleiben unberührt.
- **⚠️ Die Middleware war fail-open (live gefunden, 2026-07-29):** Ihr `except Exception` um den Nutzer-Lookup ließ den Request **durch**, wenn die Rolle nicht feststellbar war — ein DB-Aussetzer hätte einem Verkäufer die ganze App geöffnet. Jetzt getrennt: unlesbares/abgelaufenes Token → durchlassen (die Route antwortet 401, ein 403 würde einen abgelaufenen Login als Rechteproblem darstellen), **Lookup-Fehler → 503**. Aufgefallen ist das erst im Integrationstest, weil dort `/api/customers` mit **HTTP 200** antwortete, obwohl die Regel korrekt war.
- **⚠️ Und die Middleware wurde von den Integrationstests nie ausgeführt:** Sie öffnet ihre **eigene** Session (hängt nicht an `get_db`, ist also nicht über `dependency_overrides` umbiegbar) und zeigte im Test auf die konfigurierte `DATABASE_URL`. Der Fehler wurde geschluckt → die Prüfung fiel still aus. Die `sessionmaker`-Fixture patcht `app.database.async_session_factory` jetzt mit; damit prüfen **auch die 12 bestehenden Mandanten-Tests** die Middleware mit.
- **Papierkorb statt hartem Löschen — ein Codepfad für alle Rollen** (`rainmaker_leads.deleted_at`/`deleted_by_id`, Migration `scripts/add_lead_soft_delete.sql`, **vor Deploy**): `DELETE /leads/{id}` markiert nur, der Lead verschwindet sofort aus allen Ansichten, bleibt `TRASH_RETENTION_DAYS`=30 wiederherstellbar; der Cron entfernt ihn danach endgültig. Bewusst kein „Verkäufer weich, Inhaber hart": weniger Fehlerfläche, und ein Papierkorb nützt dem Inhaber genauso.

### Legal-Compliance-Tracking (Rechtsdokumente)
Stellt sicher, dass jeder Kunde die Pflicht-Rechtsdokumente (Default **AGB + AVV**) unterschrieben vorliegen hat. Router `routers/compliance.py` (`/api/compliance/*`): `GET /overview` (alle Kunden × Pflichtdocs, Lücken zuerst), `GET /customer/{id}`, `POST /mark` (manuell ab-/anhaken), `POST /upload` (unterschriebenes PDF → legt einen `attachments`-Eintrag an **und** den Compliance-Record an), `PUT /templates/{id}/required` (Pflicht-Flag toggeln).
- **Pflicht-Set ist konfigurierbar** über die neue Spalte `document_templates.compliance_required` (nullable: `NULL`=nie konfiguriert → Seed setzt Default für AGB+AVV; `true/false`=Nutzerwahl bleibt bei Re-Seed erhalten). **Spalte via manuellem `ALTER` auf bestehende Tabelle** (`ALTER TABLE document_templates ADD COLUMN compliance_required boolean;`), danach Seed nachziehen.
- **`compliance_records`** (auto-erstellt via `create_all`): eine Zeile pro (Kunde, Vorlage), unique. `signed_at` gesetzt = erfüllt; `method` = `upload`|`manual`; `attachment_id` verweist auf die hochgeladene Datei. „Erfüllt" wird daraus berechnet — Anhänge bleiben die Single Source of Truth für die Datei.
- **Frontend**: Nav-Seite **Rechtsdokumente** (`/rechtsdokumente`, `pages/Compliance.tsx`) mit Summary + Pro-Kunde-Karten (PDF erstellen / Hochladen / Abhaken) + Pflicht-Konfiguration. Im Kundendetail: Header-Badge „Legal" + `CustomerComplianceCard` im Dokumente-Tab. PDF-Erstellung nutzt die bestehenden `routers/documents.py`-Endpoints.

Tables are auto-created on startup via `Base.metadata.create_all`. New columns on existing tables require manual `ALTER TABLE` on the running DB container. **Bekannte Folge: Entwicklungs-Datenbanken driften.** Weil `create_all` neue Spalten NICHT nachzieht, fehlten in einer lokalen DB zuletzt 18 Spalten, während die Produktion korrekt war (die Migrationen wurden dort ja gefahren). Beim Aufsetzen einer frischen Entwicklungs-DB oder nach längerer Pause die `backend/scripts/*.sql` durchlaufen — oder die DB wegwerfen und neu anlegen, dann baut `create_all` das vollständige Schema. Backup auto-discovers all tables via `Base.registry.mappers`.
